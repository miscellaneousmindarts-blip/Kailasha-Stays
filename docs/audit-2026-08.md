## Headline finding

**The lag you're feeling is real, it's reproducible, and it has one dominant
cause.** It is not general slowness — the server is fine. It's that on some
routes the browser sits on the *old* page, completely frozen, with zero
feedback, for 2–3 seconds after a click.

Measured, clicking between the two main public pages:

| Navigation | Frozen for | Why |
|---|---|---|
| `/properties` → `/` (homepage) | **~2000–3000 ms** | dynamic render, **no `loading.tsx`** |
| `/` → `/properties` | **15–150 ms** | SSG **+ has `loading.tsx`** |

Same app, same session, ~20× difference. That's the whole story: the routes
that have a loading boundary feel instant, and the routes that don't feel
broken. Your instinct in the brief was correct.

# Part 1 — Code

## 1.1 Critical

### C1 · Missing loading boundaries on the highest-traffic routes

Only **3 `loading.tsx` files exist across 24 routes**. The gaps are the worst
possible ones:

| Route | Dynamic? | `loading.tsx`? | Impact |
|---|---|---|---|
| `/s/[tenant]` — **marketing homepage** | ✅ force-dynamic | ❌ | 2–3 s freeze |
| `/stay/[token]` — **guest portal** | ✅ force-dynamic | ❌ | freeze on every guest visit |
| `/superadmin` | ✅ | ❌ | freeze |
| `/(platform)` apex | — | ❌ | freeze |
| `/admin/*` | ✅ | ✅ (shared) | OK — see U3 |
| `/s/[tenant]/properties[/slug]` | SSG+ISR | ✅ | fast |

In the App Router, a navigation without a Suspense boundary between the two
routes means React holds the old UI on screen until the *entire* new route is
ready. No spinner, no skeleton — the app looks hung. That is exactly the
symptom you described.

**Fix — do this first.** Add a `loading.tsx` next to each of the four routes
above. This alone converts the 2–3 s freeze into an instant skeleton. It's
about 30 minutes of work and needs no architectural change.

Next.js's own docs confirm the ordering: route-level `loading.js` is the
primary fix; `useLinkStatus` (available in this version, `next/link`) is for
inline per-link feedback *after* that.

### C2 · The homepage pays a dynamic render on every single visit

`app/(public)/s/[tenant]/page.tsx` is `force-dynamic` for one reason, stated
in its own comment: the hero swaps its H1 on `?src=` for ad message-match.

The cost of that decision, measured:

- **Cold TTFB: 2.53 s** (serverless cold start)
- Warm TTFB: 0.24–0.52 s
- Property pages, by contrast (SSG+ISR): 0.16–0.22 s

So the single most important page for converting a visitor — the one an ad
click lands on — is also the slowest and the only one that can cold-start into
a 2.5 s blank wait.

**Options, in increasing order of effort:**

1. **Add `loading.tsx`** (C1). Doesn't make it faster, but removes the *frozen*
   feeling. Do this regardless.
2. **Isolate the dynamic part.** Keep the page static and put only the
   `?src=`-dependent hero copy inside a `<Suspense>` boundary, so the shell,
   nav, images and everything below the fold prerender. Best
   effort-to-payoff ratio.
3. Partial Prerendering — this Next version ships PPR docs
   (`node_modules/next/dist/docs/01-app/02-guides/ppr-platform-guide.md`).
   Bigger change; worth reading before committing to it.

### C3 · Duplicate migration number `0022` — this already caused an outage

```
supabase/migrations/0022_block_only_images.sql
supabase/migrations/0022_booking_calendar_block_flag.sql   ← never ran
```

Two different migrations share the number `0022`, and there is **no migration
tracking table** anywhere in the project — ordering and applied-state are both
tracked by hand.

This is not theoretical. It is the direct cause of today's production
incident: `0022_booking_calendar_block_flag.sql` was skipped, `blocks_calendar`
never got created, and **booking creation broke in production** with
`Could not find the 'blocks_calendar' column`. The collision made it genuinely
ambiguous whether "0022" had been run.

**Fix:**
- Rename the unapplied-order file to `0024_…` so the sequence is total again
  (content is idempotent — `add column if not exists` — so renaming is safe).
- Adopt an applied-migrations table, or move to the Supabase CLI's own
  migration tracking, so "did this run?" stops being a question answered by
  memory.

### M3 · Three oversized client components

| File | Lines | `"use client"` |
|---|---|---|
| `components/admin/homepage/builtin-editors.tsx` | 1181 | ✅ |
| `components/admin/booking-detail.tsx` | 729 | ✅ |
| `components/admin/homepage/homepage-shell.tsx` | 663 | ✅ |

`booking-detail.tsx` holds ~8 sibling section components in one file
(`BasicsSection`, `PricingSection`, `PortalLinkSection`, `AddonsSection`,
`BillingSection`, `DocumentsSection`, `CancelSection`…). It works, but it's the
file most likely to cause a merge conflict and the hardest to navigate. Since
all three are client components, their full weight ships to the browser.

Splitting these is low-risk, mechanical, and would meaningfully improve both
the admin bundle and day-to-day editing. Not urgent.

### M4 · Client/server split is heavier than it needs to be

**90 of 162 components (55%) are `"use client"`.** For an admin-heavy app that
isn't automatically wrong, but it's high enough to be worth one deliberate
pass — particularly the guest-portal and landing components, which are the
ones real customers download over mobile data.

## 1.3 What's genuinely good

Worth saying plainly, because it's most of the codebase:

- **Indexes are thorough** — 25 explicit, plus the right implicit ones
  (`bookings.portal_token unique`, `properties (tenant_id, slug)`). The guest
  portal's hot lookup path is properly indexed.
- **Multi-tenancy was corrected properly.** `properties.slug` started globally
  unique in `0001`; `0012` correctly dropped it and re-scoped to
  `(tenant_id, slug)`. That's the kind of thing that usually rots — it didn't.
- **No N+1 queries found.** `Promise.all` is used consistently in 20 places,
  including the iCal sync fan-out.
- **The guest portal is one RPC round trip** (`get_booking_by_token`), not a
  dozen chained queries. Good design.
- **Images are handled well** — `priority` correctly on above-fold hero/gallery,
  blur placeholders, explicit `sizes`, and only 2 raw `<img>` tags (both admin
  preview widgets, both legitimate).
- **`npm run typecheck` and `npm run lint` are clean** (the only 4 warnings come
  from `silver-oak-menu/`, an unrelated vendored folder).

# Part 2 — UX & visual design

## 2.1 The freeze is a UX problem before it's a perf problem

Re-stating C1 in product terms, because this is the single biggest thing
standing between the app and feeling "smooth":

A 2–3 second freeze with **no feedback** is worse than a 4-second load *with* a
skeleton. Users don't experience latency, they experience uncertainty — a frozen
screen reads as "broken", and the most common response is a second click, which
makes it worse. Every other item in this section is cosmetic next to this one.

## 2.2 Guest portal — property title truncates on mobile

[components/guest-portal/portal-header.tsx:64](components/guest-portal/portal-header.tsx#L64)

```
"Premium 2BHK Apartment"  →  renders as  "Premium 2B…"
```

`truncate` (single-line ellipsis) on the `<h1>`, next to a `shrink-0` "View
listing" button that reserves ~230 px of a 375 px screen. The guest's first
view of their own booking shows a property name they can't read.

This also contradicts your own standing design rule in `~/.claude/CLAUDE.md`:

> `truncation-strategy` — Prefer wrapping over truncation; when truncating use
> ellipsis and provide full text via tooltip/expand

**Fix:** `line-clamp-2` instead of `truncate`, or stack the button below the
title on mobile. Two-line titles are fine here — there's vertical room.

## 2.3 Admin — one generic skeleton for eight differently-shaped pages

[app/admin/(dashboard)/loading.tsx](app/admin/(dashboard)/loading.tsx) is
explicitly "deliberately generic": a heading, **4 stat tiles**, and a list.

But only **one** admin page actually looks like that — the dashboard index.
Verified: `calendar`, `settings`, `homepage`, `bookings`, `enquiries`,
`listings`, `addons`, `more` have **zero** stat tiles.

So on 8 of 9 admin pages the skeleton promises a layout that never arrives, and
the content visibly jumps when it settles. A mismatched skeleton can feel worse
than a plain spinner, because it sets a false expectation.

**Fix:** either add per-route `loading.tsx` files for the 2–3 highest-traffic
admin pages (bookings, calendar), or make the shared one shape-neutral — a
title bar plus generic content blocks, no stat tiles.

## 2.4 Platform apex page — half an empty screen, and no way in

[app/(platform)/page.tsx](app/(platform)/page.tsx) uses
`flex flex-1 items-center` to vertically centre a short block of text. On a
375×812 mobile viewport that leaves **~430 px of blank space above the
headline** — over half the first screen is empty.

There is also no call to action of any kind. The code comment is candid about
this ("nothing for a visitor here to actually do"), and invitation-only
onboarding is a legitimate product choice — but a homestay owner who *does*
want in currently has no next step, not even a mailto.

**Fix:** top-align on mobile (`items-start` with padding, `md:items-center`),
and add one contact affordance.

## 2.5 Visual coherence — strong, keep it

The design system is the healthiest part of this app:

- **Consistent type scale and weights** across landing, portal and admin
  (verified by dumping computed styles — 12/14/16/24/26/28 px, weights 400/500/600).
- **Semantic colour tokens** (`text-text-muted`, `border-border`,
  `bg-surface-subtle`, `text-primary`) used almost everywhere rather than raw hex.
- **Brand colour is per-tenant** and cascades via CSS custom properties from the
  layout — genuinely white-label.
- **The bilingual hero is handled with real care** — Hindi and English H1s
  stacked with distinct sizes rather than a language toggle, which is right for
  a family audience forwarding links on WhatsApp.
- **The distances bento deliberately matches the homepage "Where you'll be"
  tiles**, so the property page and homepage read as one product.

Two small things to check:

- Hindi H1 is weight 400 / 28 px, English H1 is weight 600 / 26 px. Probably
  intentional (Devanagari renders visually heavier), but confirm it's a decision.
- A few 14 px labels at 0.78–0.82 alpha sit over photography
  (`"15 min walk"`, `"every distance below measured…"`). Over the dark scrim
  they're likely fine, but they're the closest thing to a contrast risk in the
  app and worth one measurement against the actual images.

## Method

- Timings: `curl` TTFB against production (cold and cache-busted), plus
  in-browser click-to-route-commit measurement over 3 rounds. Millisecond
  figures from the in-browser harness are approximate — it polls on a 10 ms
  interval — but the ~20× gap between boundaried and unboundaried routes is
  consistent and well outside the noise.
- Build: `next build` on `de958f0`, clean.
- Static analysis: dead-export scan, `"use client"` census, duplicate-name scan,
  N+1 grep over `lib/` and `app/`, index inventory across all 24 migrations.
- Visual: live production site at 375×812, computed-style dump for the type and
  colour audit.
- Admin UI was assessed from source and from component-level rendering, not from
  a logged-in session.
